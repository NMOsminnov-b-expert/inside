# Проверки макета

Сценарии в браузере, которые ловят уже случавшиеся дефекты.

## Два этапа

По ходу работы прогоняется не всё, а то, чего касается правка. Полный прогон —
перед коммитом и перед отчётом пользователю.

```
python tools/checks/run.py --changed       # этап 1: только затронутое правкой
python tools/checks/run.py                 # этап 2: всё
```

Так сделано после замера 07.09.2026: полный прогон занимал 157 с, и платить их
за правку одной строки не за что (требование пользователя — «на минимальные
правки уходит куча затрат, это не дело»).

Остальные ключи:

```
python tools/checks/run.py архив ЕНИ       # только названные (по части имени)
python tools/checks/run.py --list          # что есть и от каких файлов зависит
python tools/checks/run.py --show          # с открытым браузером, чтобы смотреть
python tools/checks/run.py --jobs 5        # больше потоков (по умолчанию половина ядер)
python tools/checks/run.py --profile       # переходы и ожидания внутри сценариев
python tools/checks/run.py --slow          # ждать с запасом (втрое дольше предел)
python tools/checks/run.py --no-retry      # без повтора упавших
```

Нужен `playwright` (тот же, что у `tools/visual-parity`). Сервер и браузеры
поднимаются сами; отчёт печатается по мере готовности, а в конце — сводка и код
возврата `1`, если что-то провалилось.

## Как работает отбор по правкам

Каждый файл проверки объявляет `TOUCHES` — пути, от которых он зависит:

```python
TOUCHES = ('app/kernel/gps.js', 'app/modules/*/oi/*')
```

`run.py --changed` берёт изменённые файлы из git (правки, индекс, новые файлы;
с `--changed main` — ещё и всё, что ветка накопила относительно `main`) и
оставляет только затронутые сценарии.

Отбор специально устроен осторожно: всё неразобранное ведёт к полному прогону,
а не к пропуску (`select_changed.py`).

| Что изменено | Что запустится |
|---|---|
| `app/kernel/gps.js` | сценарии, назвавшие этот файл |
| `app/kernel/router.js`, `app/shell/*`, сам каркас проверок | всё |
| файл, которого не назвал ни один сценарий | всё, и в отчёте видно, какой файл оказался незнакомым |
| только документация, снимки, граф знаний | ничего |

Два сценария объявляют областью весь макет (`app/*`) и потому идут при любой
правке: `check_basics.py` (экраны открываются, правки сохраняются, слушатели не
копятся) и `check_ui_text.py` (сплошной обход экранов на служебные значения в
тексте). Они и есть страховка, если у кого-то `TOUCHES` описан неточно.

## Чем полный прогон быстрее, чем был

* **один браузер на несколько файлов.** Раньше процесс поднимался на каждый
  файл, и подъём Playwright с Chromium (≈1,4 с) повторялся 25 раз — четверть
  всего времени уходила на старты. Страница у каждой единицы своя: данные макета
  живут в памяти вкладки, и сценарии не должны видеть чужие правки;
* **тяжёлые сценарии разложены на части.** Файл объявляет `PARTS` и принимает
  часть вторым доводом — `run(t, part)`. «Виды ОИ» обходили пять типов ОЦ и
  занимали 51 с из 339 с, то есть один файл держал хвост всего прогона; теперь
  это пять независимых частей плюс справочники;
* **раскладка по замерам.** `.times.json` (локальный, в git не идёт) помнит, чего
  сколько стоит: самые долгие единицы раскладываются первыми, каждая — в самый
  свободный поток;
* **отчёт по мере готовности** — провал видно на десятой секунде, а не в конце.

Разбивать на части можно только независимые проходы. `check_building_same.py`,
например, разбивать нельзя: он именно СРАВНИВАЕТ типы ОЦ между собой, и по
частям сравнение стало бы пустым.

## Что где проверяется

`python tools/checks/run.py --list` печатает полный список с областями. Ниже —
ориентир по нескольким:

| Файл | Область |
|---|---|
| `check_basics.py` | экраны всех модулей открываются, правки сохраняются, лог действий пишется, заголовок вкладки различает экраны, слушатели не копятся |
| `check_eni.py` | код ЕНИ: маска, допустимые длины 13/15/18, запрет сохранения с неверным кодом |
| `check_address.py` | адрес по частям, свёртка адресов и кодов ЕНИ, столбцы реестра |
| `check_flags.py` | один значок ML вместо двух, цвет особенностей, сортировка по флажкам вглубь списка |
| `check_archive.py` | документ уходит в архив и возвращается, поиск и фильтры архива, права доступа |
| `check_layout.py` | ничего не выходит за окно на 1600/1366/1152/1024, значения в полях и шапке не обрезаны |

## Как добавить проверку

Новый файл `check_<область>.py` рядом; в нём `NAME = 'что проверяем'`,
`TOUCHES = (...)` и функция `run(t)`. Объект `t` даёт:

- `t.open(маршрут)` — перейти и дождаться отрисовки;
- `t.page` — страница Playwright;
- `t.ck(условие, 'что сломано, если условие ложно')` — проверка;
- `t.wait_for(селектор)` / `t.wait_until(js)` — дождаться ПО ФАКТУ;
- `t.wait(мс)` — дождаться затишья DOM (число — предел, а не пауза);
- `t.text()` — текст страницы.

`run.py` подхватит файл сам. Ошибки в консоли браузера считаются провалом
автоматически — отдельно проверять их не нужно.

Ждать надо по факту, а не отсчётом времени. Это не вкусовое правило: разбивка
«видов ОИ» на части сразу вскрыла проверку, которая держалась на том, что
карточка квартиры уже в кэше модулей браузера от предыдущего типа ОЦ. Пока
сценарий шёл одной страницей, любое ожидание «успевало»; со своей страницей у
каждой части — перестало.

В шапке файла стоит написать, какой именно дефект сценарий ловит: через полгода
это единственный способ понять, можно ли проверку менять.
