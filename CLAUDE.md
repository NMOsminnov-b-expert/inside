# Макет «inside» — правила работы

Выжимка. Полный текст правила, повод и цитата — в графе знаний
(`graph.py show <id>`); действующие правила хук SessionStart
(`tools/hooks/session_start.py`) кладёт в начало каждого разговора.
Подробности устройства — в CLAUDE.md при папках: `app/`, `tools/knowledge/`,
`tools/checks/`, `tools/matrix/`, `tools/visual-parity/`. Сокращено 17.11.2026
при разборе правил с пользователем («Пора эту солянку почистить»).

## Данные проекта наружу не уходят

Правило `dannye-proekta-naruzhu-ne-uhodyat` (15.09.2026). Репозиторий макета
публичный — в нём только тестовые данные.

* не публиковать документы, отчёты, снимки и код в артефакты, облачные
  сервисы и чужие репозитории;
* не отправлять содержимое файлов, названия полей, словари, адреса и
  структуру данных в поисковые запросы и внешние инструменты; интернет —
  только чтение, запрос общими словами;
* **`git push` — только по прямой просьбе пользователя** (хук спрашивает);
  публикация пакетов запрещена;
* в git не идут `docs/`, `data/local/`, ответы Кадастра и Дарека, граф,
  архивы и таблицы (хуки pre-commit и pre-push).

Можно наружу: модель и производитель при опознании позиций описей, подложка
карты OSM, адреса объектов — во внешний геокодер, ЕНИ — на внешние сервисы.
К диску Y: и папкам с исходными фото не обращаться.

## Как работать

* **Объяснять как человеку вне контекста**: откуда термин, где это в
  интерфейсе, для чего.
* **Бизнес-логику — спрашивать**, код и дизайн — решать самому. Где решение
  зависит от бизнес-процесса (что значит поле, как считается величина,
  «так задумано или упрощение макета») — сразу спросить.
* **Граф знаний** — один поиск по словам (`graph.py find` или `codegraph`),
  когда нужен ответ про бизнес-процесс. Записывать — правила и ответы
  пользователя на бизнес-вопросы, командами `graph.py new | add | set`;
  файлы `knowledge/` руками не править. Поиск по смыслу (semsearch) не
  используется (17.11.2026). Запись о коде — с `--code <путь>`; перед
  правкой файла — `graph.py code <путь>` (знание о нём); после коммита хук
  называет записи о задетых файлах — сверить (17.11.2026, по образцу UnDiscord).
* **Коммиты** — в ветку `refactor`, ветки не создавать и не вливать без
  указания. Автор — человек; в конце описания «Задача: Осминнов Н.» (две
  «н»); `Co-Authored-By: Claude` не ставить (хук commit-msg).
* Ничего не удалять без прямого указания.

## Интерфейс

* Снимки (`tools/visual-parity/report.py`) — для новых экранов, на ширине
  телефона и компьютера; просмотреть до отчёта. Практики (`ui-ux-pro-max`,
  интернет) — только для нового вида элемента.
* Окна, перекрывающие экран, — нет; всплывающие окна (попапы) у места
  действия — можно. Оформление — только из токенов и примитивов ядра.
* Подписи — существительными; в интерфейсе только факты; подсказки не
  выходят за край экрана; у огромных списков нет «показать всё».

## Проверки

Подробности — `tools/checks/CLAUDE.md`. Поведение — сначала по коду, затем
сценарием. Гонять точечно (названные сценарии или `--changed`); полный
прогон и прогон матрицы — по просьбе. Сценарий покрывает ветки поведения,
задетые правкой; нет данных — создать. Новый экран — строка в
`tools/matrix/screens.py`. В отчёте — что гонялось.

## Документы

* Человеку — `.docx` или `.xlsx`, собранные скриптом в `tools/docs/`;
  Markdown — только записки разработчику рядом с кодом. Документ описывает
  систему, а не себя. Действующее лицо — пользователь, а не «оценщик».
* ТЗ — только в графе (записи `tasks` «ТЗ: …»).
* Перед пересборкой docx или xlsx — проверить, что пользователь его не
  правит.
* Вся `docs/` — вне git; раскладка: `docs/реестры`, `docs/поля-и-справочники`,
  `docs/осмотры`, `docs/тз`, `docs/сверки`, `docs/аудиты-и-разборы`,
  `docs/api`, `docs/устройство`, `docs/снимки`, `docs/источники/…`,
  `docs/архив`, `docs/граф-выгрузки`.
