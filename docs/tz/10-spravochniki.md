# ТЗ — Справочники

Отдельная вкладка системы. Справочник — это перечень допустимых значений для
поля с выбором. Сегодня такие перечни зашиты в код (`modules/*/data/dictionaries.js`),
и поменять их может только разработчик; после внедрения ими управляет
администратор из интерфейса.

Решения, принятые пользователем 02.09.2026 (не переоткрывать):

| Развилка | Решение |
|---|---|
| К чему привязывается справочник | К **полю конкретного типа ОИ внутри типа ОЦ**: тип ОЦ → тип ОИ → поле. **Один справочник — одно поле** (уточнение 02.09.2026: общий перечень на несколько полей разнесён — «иначе система станет сложнее»). |
| Каталоги | Жёсткие: **тип ОЦ → тип ОИ**. Вручную не создаются — структура повторяет саму систему. Перенос справочника в другой каталог = смена привязки. |
| Папки | Внутри типа ОИ бывают **папки**: конструктивный состав — это восемь отдельных полей карточки, и они собраны в папку «Конструктивный состав». Справочник переносится в папку и обратно. |
| Перенос между каталогами | **Автопривязка по ключу поля**: привязка переходит на поле с тем же ключом. По названию справочника ничего не угадывается — если ключа в каталоге нет, система показывает поля и ждёт выбора, ничего не меняя. |
| Порядок в каталоге | Сначала обычные справочники, потом системные — вперемешку они сбивают. |
| Удаление позиции, которая используется | **Гибрид**: не используется — удаляем сразу; используется — предлагаем замену на существующую позицию либо на новую (последнее равносильно переименованию). |
| Кто правит | **Администратор и роль «любая»** (уточнение пользователя 02.09.2026: «Роль Любая роль так же должна давать доступ к редактированию»). Остальные роли — просмотр. |
| История | **Запись в общий лог действий.** Версий и отката нет; карточки всегда видят актуальный справочник. |

## 1. Что имеем сейчас

Замеры по коду на 02.09.2026:

| Показатель | Значение |
|---|---|
| Перечней в `dictionaries.js` (уникальных имён) | 41 |
| Точек использования (тип ОЦ × карточка × поле) | 133 |
| Полей выбора `<select>` в разметке | 106 |
| Мультивыборов (`.ms-drop`) | 15 |
| Перечней, уже разошедшихся между модулями | 3 |

Разошлись `APARTMENT_SERIES` (7 против 8 значений), `LAND_ENCUMBRANCE`
(2 против 3) и `MANSARD_TYPE` — последний хуже всех: в четырёх модулях это
конструктивный тип мансарды, а в `civil` под тем же именем лежит форма крыши.
Пять копий одного перечня расходятся ровно так, как и должны были: незаметно.

### 1.1. Не всё, что похоже на справочник, им является

Часть перечней управляет **логикой**, а не просто наполняет список. Их правка
из интерфейса сломает поведение карточек, поэтому они остаются в коде и в
разделе справочников показываются только для чтения, с пометкой «системный».

| Перечень | Что сломается при правке |
|---|---|
| `STATUS_OC`, `STATUS_BUILD` | этапы процесса: сортировка реестра, доступ ролей |
| `LAND_TYPES` | выбор между блоками «Сельскохозяйственные» и «Несельскохозяйственные» |
| `LAND_ENCUMBRANCE`, `LAND_BUILDINGS` | «Есть» открывает зависимые поля |
| `BUILD_TYPE` | «Тип строения» доступен только при вспомогательном здании |
| `CATCLASS`, `OI_CATEGORY_GROUPS` | определяют, какая карточка ОИ откроется |


Три перечня из справочников убраны совсем (решение пользователя 02.09.2026):
**литеры** («произвольная буква с цифрой, а не перечень значений»),
**ответственные** (это сотрудники — другая сущность, они назначаются, а не
выбираются из перечня) и — наоборот — **категории фотографий** переведены из
системных в обычные: их нужно уметь редактировать.

Остальные перечни — настоящие справочники: материалы и конструкции,
отопление, права, серии домов, формы и рельеф участка, полив, износ,
температурный режим, благоустройство, инженерное оснащение, типы документов.
Именно они переходят под управление администратора.

## 2. Модель данных

### 2.1. Справочник

```
dict = {
  id,                  // 'dict-014'
  name,                // 'Материалы стен · базовый'
  note,                // пояснение: когда применять
  kind,                // 'list' — плоский перечень
                       // 'group' — перечень с разделами (как конструктивный состав)
  system,              // true — из раздела 1.1: показывается, но не правится
  items: [ … ],        // позиции, см. 2.2
  bindings: [ … ],     // точки подключения, см. 2.3
  createdAt, createdBy,
  updatedAt, updatedBy,
}
```

**Конструктивный состав разнесён на восемь справочников** — по одному на поле
карточки (фундамент, наружные и внутренние стены, перекрытия, кровля, полы,
окна, двери). Они лежат в папке «Конструктивный состав» внутри типа ОИ: правило
«один справочник — одно поле» действует и здесь, потому что в карточке это
восемь отдельных полей. Поле в привязке записано через точку — `struct.foundation`.

### 2.2. Позиция

```
item = {
  id,          // устойчивый: по нему считается использование
  value,       // 'Кирпич керамический' — то, что видит оценщик
  note,        // необязательное пояснение
  group,       // раздел, если kind: 'group'
  order,       // порядок в списке, правится перетаскиванием
}
```

**Значение хранится в карточке текстом, а не ссылкой на `item.id`.** Так уже
устроены данные, и менять это сейчас — переписывать все карточки. Следствие:
переименование позиции обязано пройти по объектам и переписать значение (см. 3.3),
иначе старое название останется висеть в карточках.

### 2.3. Привязка и каталог

```
slot = {
  typeId,      // 'civil' | 'apartment' | 'residential-house' | 'production' | 'land-plot'
  card,        // тип ОИ: 'oc' | 'building' | 'apartment' | 'land' | 'movable'
  field,       // 'wallsMaterial' — ключ поля в данных карточки
  label,       // 'Материал стен' — подпись, как её видит оценщик
}
```

Привязка **одна** (`dict.slot`), и каталог из неё вытекает: `typeId + card`.
Отдельного поля «каталог» нет — иначе справочник мог бы лежать в одном месте, а
применяться в другом.

Справочник без привязки (созданный вручную или копия) попадает в служебную
ветку «Не привязаны»: карточки его не видят, и это должно быть заметно.

Каталог возможных точек собирается из описаний модулей (`data/dictExport.js`) —
133 записи. Он нужен, чтобы:

- выбирать поле из списка, а не вводить ключ руками;
- подбирать одноимённое поле при переносе между каталогами;
- ловить конфликт: одно поле — один справочник.

### 2.5. Папки внутри каталога

`dict.folder` — имя папки; пустая строка означает «лежит прямо в каталоге».
Папки не отдельная сущность: они существуют, пока в них есть справочники, и
исчезают, когда последний вынесли. Так папку нельзя «завести и забыть».

Перенос в другую папку — внутри своего каталога; при переносе в другой каталог
папка сбрасывается, потому что принадлежит каталогу, а не справочнику.

### 2.4. Где живут данные

`kernel/dicts.js` — стор справочников, один на систему. Модули к нему
обращаются через функцию `optionsFor(typeId, card, field)`, которая возвращает
значения назначенного справочника, **а если справочник не назначен — прежний
перечень из `dictionaries.js`**. Это даёт постепенное внедрение: пока поле не
переведено, оно работает как сейчас.

> **ДЛЯ СЕРВЕРНОЙ ВЕРСИИ:** в макете справочники живут в памяти вкладки. На
> сервере это отдельная таблица с правами на изменение и, вероятно, кэшем на
> клиенте: перечни читаются на каждом открытии карточки, а меняются редко.

## 3. Операции

### 3.1. Создание и копирование

- **Создать** — пустой справочник, название обязательно.
- **Копировать** — дубликат со всеми позициями, назначения **не копируются**:
  копию делают, чтобы развести перечни, а не размножить одинаковые назначения.
  Имя копии — «<имя> · копия», сразу доступно для правки.

### 3.2. Позиции

Добавление, правка значения и пояснения, порядок перетаскиванием, поиск по
списку. Дубликаты значений внутри одного справочника запрещены — при вводе
существующего значения поле подсвечивается, как это уже сделано для кода ЕНИ.

### 3.3. Удаление позиции — гибридное правило

Перед удалением система считает, в скольких объектах значение встречается.

- **Нигде не используется** → удаляется сразу, без вопросов.
- **Используется** → диалог с выбором:
  - **Заменить на существующую позицию** — значение во всех объектах переписывается
    на выбранное, позиция удаляется;
  - **Заменить на новое значение** — фактически переименование: система создаёт
    позицию с новым названием и переписывает объекты на неё;
  - **Отмена**.

В обоих случаях в лог действий каждого затронутого объекта пишется строка вида
«Материал стен: Саман → Сырцовый кирпич (замена при правке справочника)».
Отдельной строкой пишется само изменение справочника.

Диалог устроен так (замечание пользователя 02.09.2026 — «окно удаления не
проработано по дизайну»): сверху крупной цифрой последствие («47 объектов
используют это значение в поле …»), затем два способа замены крупными
карточками с полем ввода внутри выбранной, внизу таблица затронутых объектов —
код ЕНИ, адрес, карточка, статус. Кнопка подтверждения называет действие
(«Заменить и удалить» либо «Переименовать»), а не «ОК».

### 3.4. Привязка и перенос между каталогами

Блок на экране называется **«Где применяется»** и показывает цепочку из трёх
шагов: тип ОЦ → тип ОИ → поле карточки. Привязка идёт именно к типу ОИ внутри
типа ОЦ, а не к объекту оценки целиком.

- **Привязать к полю** — для справочника без привязки: выбор каталога, потом
  свободного поля в нём.
- **Перенести в другой каталог** — выбор каталога. Дальше автопривязка: система
  ищет в нём поле с тем же ключом, иначе с той же подписью. Нашла и оно
  свободно — переносит сразу; иначе показывает свободные поля каталога и ждёт
  выбора, **не меняя ничего до ответа**.
- **Отвязать** — поле возвращается к встроенному перечню, справочник уходит в
  ветку «Не привязаны».
- Одно поле — один справочник: привязка к занятому полю отбирает его у прежнего
  владельца, и тот становится непривязанным.

### 3.5. Удаление справочника

Запрещено, пока справочник привязан к полю: сначала отвязать. Справочник без назначений
удаляется с подтверждением. Системные (раздел 1.1) не удаляются никогда.

### 3.6. Права

Всё выше — администратору и роли «любая»: в списке ролей она описана как «без
ограничений — как у администратора», и лог действий с архивом уже работают по
этому же правилу (`seesEverything()` в `kernel/session.js`). Остальные роли видят раздел, состав
справочников и назначения, но все действия недоступны (кнопок нет, а не
«кнопка есть и ругается»). Правило берётся из `kernel/session.js`, тем же
способом, что доступ к логу действий и архиву.

## 4. Экран

Вкладка «Справочники» в боковом меню (сейчас там заглушка «скоро»),
маршрут `#/dicts`. Уровень детализации — не ниже карточки земельного участка.

### 4.1. Раскладка

Две колонки, как в реестре: слева список справочников, справа карточка
выбранного.

```
┌────────────────────────────┬─────────────────────────────────────────────┐
│ поиск                      │ 01 Общие сведения      [Копировать][Удалить]│
│ (тумблер) Системные   38   │    Отопление                                │
│                            │    пояснение · 8 значений · 21 вхождение    │
│ Жилое здание (дом)     21  │                                             │
│   Объект оценки         3  │ 02 Значения                     [+ Значение]│
│      Тип документа      5  │    значение · пояснение · объектов · x      │
│   Литера (строение)    11  │    + новое значение — Enter                 │
│      Отопление          8  │                                             │
│      Статус (замок)     2  │ 03 Где применяется   [Перенести][Отвязать]  │
│   Квартира              5  │    Жилое здание -> Литера -> Отопление      │
│ Квартира               18  │                                             │
│ Не привязаны            1  │ 04 Использование                            │
│ [+ Справочник]             │    вхождения · в деле · ни разу не выбраны  │
└────────────────────────────┴─────────────────────────────────────────────┘
```

Слева дерево каталогов: тип ОЦ → тип ОИ → справочники. Системные помечены
замком и приглушены, тумблер сверху их скрывает. Поиск раскрывает дерево и
фильтрует по названию и значениям.

### 4.2. Блок 01 «Общие сведения»

Название, пояснение, вид (плоский/с разделами), пометка «системный». Счётчики:
позиций, назначений, объектов, где встречаются значения. Действия: копировать,
удалить.

### 4.3. Блок 02 «Значения»

Таблица с **невидимыми полями**: рамка появляется на строке под курсором и
становится настоящим полем при фокусе — сорок рамок подряд рябят в глазах.
Значение добавляется строкой в самой таблице (Enter оставляет курсор там же),
порядок правится перетаскиванием за ручку, крестик удаления проявляется на
строке. Поиск по списку — при 42 позициях конструктивного состава без него
никак. Для `kind: 'group'` строки сгруппированы разделами с заголовками.

Колонка «Объектов» — не украшение: по ней видно, какие позиции реально живут, а
какие завели и забыли. Клик по числу открывает список объектов.

### 4.4. Блок 03 «Где применяется»

Цепочка из трёх плиток: тип ОЦ → тип ОИ → поле карточки, под ней фраза
человеческим языком («оценщик видит эти значения в поле … карточки … у объектов
типа …»). Технических ключей полей на экране нет.

Действия: «Перенести в другой каталог» (выбор каталога, дальше автопривязка) и
«Отвязать». У непривязанного справочника — «Привязать к полю».

### 4.5. Блок 04 «Использование»

Сводка: сколько объектов используют справочник, разбивка по типам ОЦ, список
позиций, не встречающихся нигде. Отсюда же — выгрузка списка объектов.

### 4.6. Состояния

- **Ничего не выбрано** — приглашение выбрать справочник слева.
- **Справочник пуст** — «Ни одной позиции. Добавьте первую».
- **Нет прав** — раздел открыт, действия скрыты, наверху строка о том, кто правит.

## 5. Порядок работ

| Этап | Содержание | Результат |
|---|---|---|
| 1 | Модель `kernel/dicts.js`, каталог точек `kernel/dictSlots.js`, начальное наполнение из `dictionaries.js` | справочники существуют, интерфейса нет |
| 2 | Экран `pages/dicts`: список, блоки 01–04, права | администратор видит и правит |
| 3 | Операции: копирование, назначения, гибридное удаление с заменой | полный цикл управления |
| 4 | Подключение полей: `optionsFor()` в модулях вместо прямых импортов | карточки читают справочники |
| 5 | Сведение разошедшихся перечней (раздел 1) в общие справочники | одна копия вместо пяти |

Этапы 1–3 не трогают карточки: пока поле не переведено на `optionsFor`, оно
работает как сегодня. Это позволяет остановиться после любого этапа.

## 6. Что проверяем автоматически

Новый файл `tools/checks/check_dicts.py`:

- создание, переименование, копирование справочника;
- добавление и правка позиции, запрет дубликатов;
- удаление неиспользуемой позиции — без вопросов;
- удаление используемой — замена на существующую и замена на новую, с проверкой,
  что значение переписалось в карточке объекта и попало в лог действий;
- привязка, отвязка и перенос между каталогами: автопривязка на одноимённое
  поле, а при его отсутствии — предложение выбора без изменения привязки;
- запрет удаления привязанного справочника;
- дерево каталогов «тип ОЦ → тип ОИ», системные перечни помечены и скрываются
  тумблером;
- права: неадминистратор не видит действий, прямая ссылка не даёт править;
- после перевода поля (этап 4) — карточка показывает значения справочника, а не
  встроенного перечня.

## 7. Открытые вопросы

1. **Разделы конструктивного состава** — их состав (фундамент, стены, кровля…)
   тоже редактируемый или это фиксированная структура карточки?
2. **Мультивыборы** (отопление, благоустройство, инженерное оснащение) — у них
   те же справочники, что у одиночного выбора, или отдельный вид?
3. **Импорт/выгрузка** справочника файлом — нужен ли на этом этапе (перечни
   материалов удобно готовить в таблице).
4. **Учреждения**: сейчас справочники общие для всей системы. Понадобится ли
   учреждению свой перечень материалов — и тогда права смещаются с «только
   администратор» на «администратор + свои учреждения».
