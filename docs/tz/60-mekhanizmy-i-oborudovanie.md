# ТЗ — Механизмы и оборудование

Новый, шестой тип объекта оценки (рядом с apartment/civil/production/
residential-house/land-plot). Ставится в один ряд с остальными в
«+ Создать ОЦ» (`app/kernel/registry.js`), но устроен иначе: у него нет ни
одного объекта имущества — сам объект оценки уже есть единица техники
(станок, экскаватор, генератор и т.п.), а не здание/участок с литерами
внутри.

Решения пользователя 07.09.2026 (не переоткрывать):

| Развилка | Решение |
|---|---|
| Модуль или подкатегория | **Самостоятельный тип ОЦ**, не расширение существующего модуля |
| Объекты имущества (ОИ) | **Нет** — сам ОЦ уже единица техники |

## 1. Основные параметры (карточка «01»)

Как у остальных модулей (Тип ОЦ, Статус ОЦ, Учреждение, Подвед, Адрес), но
**без** трёх полей, которые есть у пяти прежних модулей:

- код ЕНИ,
- назначение по ТП,
- GPS-координаты.

Категория ОЦ — как и везде, `<select disabled>`, но значение зафиксировано
модулем: «Движимое» (`app/modules/mechanisms/manifest.js: category`). Хук на
это уже существовал в `kernel/typeChange.js` (`changeOcType`) — записью
`taken.category = to.manifest.category`, просто им до сих пор не пользовался
ни один модуль.

## 2. Конструктор полей (карточка «02»)

Заменяет чекбокс «Имущественный комплекс» и раздел «Состав и тип имущества».
Запись ОЦ может описывать **сразу несколько механизмов** (уточнение
пользователя 07.09.2026): `rec.mechanisms = [{ id, name, qty, cost,
fields: [{id, label, value}], photos: [{id, name, dataUrl}] }]` — список,
не одна запись. Кнопка «+ добавить механизм» добавляет ещё одну; «✕ убрать
механизм» — убирает (если убрали последнюю оставшуюся, список не остаётся
пустым — подставляется одна свежая пустая запись, ОЦ всегда описывает хотя
бы один механизм).

У каждой записи механизма:

- **Название** — текстовое поле с историей (HTML `<datalist>`
  всех использованных ранее названий, `data/fieldTemplates.js: allNames()`).
  Можно вписать новое или выбрать использованное раньше.
- Набор полей всегда пересобирается под текущее название (уточнение
  пользователя 07.09.2026): выбрано **уже использовавшееся** название — под
  него подставляется набор полей (только подписи, без значений), который
  заводили для этого названия раньше (`getTemplate(name)`); название встречается
  **впервые** — поле полностью пустеет. Смена названия отменяет то, что было
  вписано в поля до неё, — это ожидаемое поведение, а не потеря данных.
- Кнопка «+ добавить поле» — пользователь сам придумывает подпись нового
  поля, поле добавляется к текущей записи и в шаблон этого названия
  (`rememberTemplate`) — при следующем выборе того же названия оно тоже
  подтянется.
- Значение поля — тоже с историей: у подписи поля есть своя история значений
  (`valueHistory` в `fieldTemplates.js`, датаlist на инпуте) — то есть каждое
  поле по смыслу и есть тот самый «словарь» на одно поле, только не
  кернел-овый (см. ниже).
- **Количество** — обязательное, по умолчанию 1; пустое/нечисловое/⩽0 при
  потере фокуса откатывается к 1, а не блокирует сохранение.
- **Стоимость** — необязательное, по умолчанию 0; пустое/нечисловое/<0 при
  потере фокуса откатывается к 0 (уточнение пользователя 07.09.2026: сначала
  сделали обязательным с блокировкой сохранения, затем передумали — поле
  просто должно быть, заполнять не обязательно).
- **Фото** — у каждого механизма своя мини-галерея (кнопка «+ Фото» —
  файл-инпут `image/*`, «✕» на миниатюре убирает), но полноразмерный
  просмотр — в ОБЩЕМ просмотрщике записи (`parts/viewer/*`, тот же, что и у
  документов: зум, поворот, лента миниатюр), а не в отдельном окне
  (уточнение пользователя 07.09.2026: «возьми просмотрщик с других
  карточек»). Технически `mech.photos`/`mech.photoFiles` — та же форма
  счётчик+файлы, что и у остальных модулей (одна фиксированная категория
  «Фото» — у механизма, в отличие от литеры здания, нет содержательных
  категорий фото), а какой именно объект показывать, просмотрщик берёт из
  `ctx.ui.viewerPhotoTarget` (прямая ссылка на запись механизма — у него нет
  ни ОИ, ни id в `rec.oi`, по которому его иначе можно было бы найти).
- Подпись поля конструктора — обязательна: пустая подсвечивается сразу
  (красная рамка) и блокирует сохранение записи ОЦ, пока не заполнена —
  единственное реально обязательное поле во всём конструкторе.

### Почему не через `kernel/dicts.js`

Кернел-движок словарей строит список привязываемых полей (`allSlots()`)
только из статических `data/dictExport.js` каждого модуля — заранее описанных
пар (карточка, поле). Подпись поля здесь придумывает пользователь в рантайме,
привязать к ней справочник заранее нечем. Поэтому у конструктора свой,
локальный для модуля `mechanisms` механизм
(`app/modules/mechanisms/data/fieldTemplates.js`) — со своим ограничением:
**эти словари не видны и не редактируются на странице «Справочники»**. Если
это понадобится, потребуется отдельная доработка `kernel/dicts.js`
(поддержка динамических слотов) — сознательно не делалась в этой задаче.

## 3. Как ОИ внутри production и civil

В `production` и `civil` уже был вид ОИ с тем же человеческим названием —
«Механизмы и производственное оборудование» (карточка `movable`,
`kind:'МЕХ'`, фиксированные поля Наименование/Год/Заводской номер), включаемый
чекбоксом «Имущественный комплекс», продублированный копипастой в обоих
модулях. По решению пользователя он заменён общей карточкой
`app/modules/mechanisms/oi/mech/*` — переиспользуется production и civil тем
же приёмом, что и карточка земельного участка из `land-plot/oi/land/*`
(тонкий прокси-`index.js` в каждом потребителе, прямой импорт фабрики
`createMechOi` в `card/ocCard.ctrl.js`, запись в `oi/registry.js` и
`data/rules.js`). Это второе, наряду с land, осознанное исключение из правила
«`modules/* → modules/*` нельзя» (см. CLAUDE.md).

Уточнение 07.09.2026 (отменяет предыдущий абзац): «Офисная техника и мебель»
**тоже объединена** с «Механизмами и оборудование» в один пункт меню — по
прямому вопросу пользователя «зачем отдельно офисная техника, это тоже
механизм/оборудование». Старая карточка `movable`, её мастер создания
«монолит/комплекс» (`create/mech.view.js`/`ctrl.js`) и связанный маршрут
(`route.rest[0]==='new'`, `ctx.mechKind`) удалены из production и civil
целиком — в «+ Добавить ОИ» под «Движимое имущество» теперь один пункт
«Механизмы и оборудование» (`card:'mech'`).

Один ОИ этого вида — **контейнер списка** механизмов (`oi.mechanisms`, тот же
`renderMechList`/`bindMechList`, что и на карточке ОЦ модуля `mechanisms`), а
не единица техники сама по себе: можно завести сразу несколько единиц в
одном ОИ, не создавая для каждой отдельный ОИ (прямой вопрос пользователя —
раньше на каждый механизм требовался свой «+ Добавить ОИ»). Из-за этого у
ОИ этого вида нет собственного `oi.name` — везде, где имя нужно для показа
(плашка над карточкой, крошки, строка перечня ОИ, лог действий), берётся
`mechListLabel(oi.mechanisms)` (первое название + «(+N)» на остальные, см.
`parts/mechConstructor.js`); там, где переписать вызов было практически
неоправданно (сайдбар просмотрщика, часть тостов) — `oi.name` поддерживается
синхронной копией того же значения. По той же причине у карточки нет и кода
ЕНИ (`oi/registry.js: hasEni:false`) — плашка не показывает пустой чип «ЕНИ»
(жалоба пользователя: «зачем поле ЕНИ, если у механизма его никогда не было»).

Существующие сид-записи с `card:'movable'` мигрированы: код ЕНИ, год выпуска
и заводской номер стали полями конструктора (данные не потеряны). У записи-
«комплекса» (раньше — вложенные `complexItems`, что для МЕХ, что для ОФИС)
новой модели вложенного списка нет — каждый бывший узел стал отдельной
записью механизма **внутри того же ОИ** (`oi.mechanisms[]`), а не отдельным
ОИ, как в первой (уже неактуальной) версии этой миграции.
