# Inside — модульная архитектура (ветка рефактора)

Точка входа: **`app.html`** (Live Server: открыть `app.html`).
Старая сборка (`index.html`, `src/`, `styles/`, `inside.html`) не тронута — ни один
её файл не изменён, поэтому эту ветку можно смотреть рядом со старой.

```
меню ОЦ (#/)  →  карточка ОЦ (#/oc/<typeId>/<ocId>)  →  карточка ОИ (.../oi/<oiId>)
```

## Что где лежит

```
app/
  kernel/      ядро: маршрут, монтирование, реестр типов, диалоги, тосты, токены CSS
  shell/       каркас окна: сайдбар, топбар, крошки, ящик заметок
  pages/ocMenu меню выбора ОЦ: поиск, фильтры, группировка, создание
  modules/     автономные модули типов ОЦ (пять штук)
```

Правило зависимостей, которое проверяется на ревью:

* `modules/*` → `kernel` — можно;
* `modules/*` → `modules/*` — **нельзя**;
* `kernel | shell | pages` → `modules/*` — **нельзя**, кроме `kernel/registry.js`.

Ядро не знает ни одного типа ОЦ и ни одного вида ОИ. Всё предметное — в модулях.

## Как добавить новый тип ОЦ

1. Скопировать любой модуль: `cp -r app/modules/civil app/modules/tec`.
2. Поправить `manifest.js` (id, label, plural, icon, order, hint).
3. Заменить `data/seed.js` (свои записи), `data/rules.js` (какие ОИ разрешены),
   `data/dictionaries.js` (свои справочники), `records.js` (сводки и создание).
4. Перегенерировать `module.css` — это копия правил под своим корнем
   `body[data-module="tec"]` (см. «Про CSS» ниже).
5. Добавить **одну запись** в `app/kernel/registry.js`.

Больше ничего. Ни один чужой файл не затрагивается — ветки не конфликтуют.

## Как добавить вид ОИ внутри типа ОЦ

1. Папка `app/modules/<тип>/oi/<вид>/` с файлами `index.js`, `view.js`, `ctrl.js`
   (можно скопировать соседнюю).
2. Запись в `app/modules/<тип>/oi/registry.js`.
3. Строка в `data/rules.js`, чтобы вид появился в меню «+ Добавить ОИ».

Правки не выходят за пределы своего модуля.

## Контракты

### Модуль ОЦ

```js
// modules/<тип>/manifest.js
export const manifest = { id, label, plural, icon, accent, order, hint };

// modules/<тип>/records.js
export function createRecord();   // создаёт пустую запись ОЦ (статус «В заполнении»),
                                   // без аргументов — меню сразу ведёт на её форму
                                   // редактирования; отдельной формы/диалога создания
                                   // на уровне меню нет — создание подхватывается
                                   // из модуля этого же ОЦ.

// modules/<тип>/index.js
export function main(host);              // ГЛАВНАЯ ФУНКЦИЯ: монтирует карточку ОЦ
// возвращает { onRoute(route), destroy() }
```

`host`, который даёт ядро:

```js
host = {
  root, scope,             // DOM-скоуп модуля: только root.querySelector
  route,                   // { typeId, ocId, rest: [...], query: {} }
  navigate(patch), hrefFor(patch), toMenu(),
  setCrumbs(items), setDrawer(conf), updateDrawer(),
  toast, confirm, prompt, select,   // общий визуал диалогов
  ensureStyle(href),
}
```

### Сводка и запросы для реестра (модуль → меню)

Реестр рассчитан на десятки тысяч записей, поэтому модуль отдаёт не «все
сводки», а страницы по запросу:

```js
// modules/<тип>/records.js
export function queryRecords({ filter, sort, offset, limit })  // → { rows, total }
export function countRecords(filter)                           // только количество
export function facets(filter)                                 // счётчики по полям
export function locate(query)                                  // точные совпадения: ЕНИ, литера, адрес
export function getSummary(id)
export function loadRecord(id)          // ленивая материализация записи
export function totalCount()
export function setStatus(id, status)               // из массовых действий реестра
export function assignResponsible(id, role, person)
```

Меню складывает страницы модулей (k-way merge в `pages/ocMenu/query.js`) и
пересчитывает общий порядок. Форма сводки:

```js
{
  id, typeId, typeLabel, typeIcon,
  title, subtitle, eni, status, city, institution, purposeTP,
  resp: { gov, cod, appr, insp },
  badges: [{ label, tone }],            // tone: 'status' | 'info'
  facts:  [{ label, value, mono? }],
  metrics: { oiCount, area, photos, docs, pendingNotes },
  flags:   { ml, mlUnverified, defects, pendingNotes },
  letters: ['А', 'Б'],                  // для поиска «лит А»
  search,                               // строка в нижнем регистре
  updatedAt,
}
```

Форма фильтра (её смысл общий для всех модулей, поля — в `data/query.js`):

```js
{
  q,                                    // строка поиска
  status: [], typeId: [], city: [], institution: [], insp: [],
  flags: [],                            // 'pendingNotes' | 'mlUnverified' | 'defects' | 'ml'
  staleDays,                            // без движения N+ дней
  mine: { role, person } | null,         // «мои объекты» по роли
  today,
}
```

### Карточка ОИ (внутри модуля)

```js
// modules/<тип>/oi/<вид>/index.js
export const card = {
  id,
  init(oi),            // ленивая доинициализация данных (например, этажи)
  render(ctx, oi),     // HTML карточки, включая свою «шапку действий»
  bind(ctx, oi),       // обработчики; всё через ctx.scope, не через document
};
```

Метаданные вида ОИ (метка, чипы плашки, столбцы перечня) — в
`modules/<тип>/oi/registry.js`, чтобы перечень ОИ, крошки и плашка не знали
про конкретные виды.

## Про CSS

* `kernel/tokens.css` — переменные, reset, кнопки, пилюли, дропдауны, тосты, модалки.
* `shell/shell.css` — только каркас окна.
* `pages/ocMenu/ocMenu.css` — меню (со своей копией базовых правил карточек/полей).
* `modules/<тип>/module.css` — **копия** правил карточек, полей, таблиц,
  аккордеонов и просмотрщика, ограниченная корнем `body[data-module="<тип>"]`.

Копии намеренные: типы ОЦ должны расходиться независимо. На старте все копии
идентичны, поэтому визуал совпадает со старой сборкой попиксельно.
Ядро ставит `document.body.dataset.module` при монтировании модуля — так стили
разных модулей не пересекаются даже после того, как оба CSS загружены.

## Меню ОЦ — реестр

Плоский список всех ОЦ, без привязки к учреждениям (разделы по учреждениям —
в других частях системы). Приоритет — ПК и люди, привыкшие к Excel, поэтому
единственное представление — таблица, а интерфейс намеренно нежирный:

1. **Локатор** — одна строка, распознаёт формат ввода: 4+ цифр → ЕНИ,
   «лит А» → литера, остальное → адрес и учреждение. Enter на единственном
   совпадении открывает карточку, минуя список.
2. **Строка срезов** — именованные фильтры-чипы со счётчиками («мне осмотреть»,
   «с невып. заметками», «ML без проверки», «без движения 30+ дней»). Счётчики
   кэшируются и пересчитываются при смене данных или роли.
3. **Фасеты слева** — тип ОЦ, статус, учреждение, город, осмотрщик, признаки.
   Счётчик каждого фасета считается без учёта самого этого фасета, поэтому после
   первого выбора остальные варианты не исчезают. Аналог автофильтра Excel.
4. **Таблица** — виртуализированная: в DOM только видимые строки, запрос идёт
   ровно за нужный срез, поэтому 20 000 записей ведут себя как 20. Сортировка по
   клику на заголовок, настройка столбцов, две плотности строк, множественный
   выбор, массовые действия (осмотрщик, статус), выгрузка **CSV для Excel**
   (`;` и BOM — открывается двойным щелчком).
5. **Превью справа** (Ctrl+клик или Space) — состав ОИ и невыполненные заметки
   без перехода в карточку.
6. **Клавиатура**: `/` — в поиск, `j`/`k` — по списку, Enter — карточка,
   Space — превью, Esc — закрыть.

Состояние выборки лежит в адресе (`#/?q=…&status=…&mine=insp`) — ссылку на
подборку можно переслать; возврат из карточки не сбрасывает фильтр.

**Демо-объём.** В подвале переключатель «только сид / 1 000 / 5 000 / 20 000
синтетических». Генератор детерминированный (`data/bulk.js` + `bulkPools.js`),
отдаёт сводки, а полная запись собирается лениво при открытии карточки
(`data/bulkRecord.js`) — как и будет с реальным бэкендом: список — сводки,
карточка — запрос. В продакшене этот переключатель удаляется вместе с тремя
файлами `data/bulk*.js`.

Замеры на 20 000 записей (headless Chromium в контейнере): фасеты со всеми
счётчиками — 23 мс, подсчёт итога — 1 мс, выборка окна таблицы — 12 мс.

## Проверка визуала

`tools/visual-parity/compare.py` поднимает старую и новую сборку, проходит
12 состояний и сравнивает область контента попиксельно.
Текущий результат: **11 из 12 состояний — 0 отличий**; форма ОЦ отличается
только двумя полями, которые теперь заблокированы (см. ниже).

## Что сделано иначе, чем в макете

Исправленные дефекты (визуал не менялся):

1. Ручной ввод «Прочее» в конструктивном составе сохраняется (`oi.structOther`)
   и появляется сразу при выборе. В макете поле было без привязки и очищалось.
2. Строки комплекса в мастере МЕХ/ОФИС живут в состоянии модуля и попадают в
   созданный ОИ (`complexItems`). В макете они существовали только в DOM.
3. Документ, прикреплённый из пустого просмотрщика, уходит в тот раздел, который
   открыт (ОИ / ОЦ / мастер). В макете всегда в документы ОЦ.
4. ЕНИ нового ОИ считается от максимума занятых, а не от длины массива —
   после удаления ОИ коды больше не повторяются.
5. Перерисовка тегов отопления совпадает с первым рендером (в макете после
   взаимодействия пропадали `&nbsp;` и `title`).
6. Метка группы заметок берётся из метаданных карточки ОИ — у движимого больше
   нет «Лит · » без литеры.
7. `prompt()` / `confirm()` заменены модальными окнами в стиле системы.
8. Удалён мёртвый CSS (`.dd-combo*`, `.dd-menu-series`, `.letter-badge`) и
   дубли между `app.css` и `layout-fixes.css`.

Осознанные изменения поведения:

* В форме ОЦ поля «Тип ОЦ» и «Категория ОЦ» заблокированы: тип = модуль.
  Перенос записи между типами — отдельная задача (нужен обмен данными между
  модулями, что архитектурой сознательно запрещено).
* Вкладка и открытый ОИ теперь в адресе (`#/oc/<тип>/<ocId>/oi/<oiId>?tab=docs`) —
  ссылку можно переслать, F5 не сбрасывает экран.
* Меню ОЦ переписано под масштаб: вместо плиток-каталога — табличный реестр
  с локатором, срезами, фасетами и виртуализацией.

## Осталось на согласование

* `.ms-drop` / `.ms-opt` (список отопления) в исходном CSS не описаны вообще —
  дропдаун рисуется без оформления. Сохранено 1:1; чинить или нет — решаете вы.
* `oi.premises` и справочник `PREM_CAT` есть в данных, UI перечня помещений
  отсутствовал и в макете. Перенесено как есть (в модулях полей нет).
